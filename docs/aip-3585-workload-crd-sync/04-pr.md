# PR 문구

base: `develop` / head: `feat/AIP-3585`

---

## Title

```
feat: 업데이트된 워크로드 CRD 를 모델·예시에 반영 (AIP-3585)
```

## Summary

cluster10 에 배포된 워크로드 CRD 3종(`Operation` v1alpha1 · `Workspace` v1beta1 ·
`ServiceExposure` v1alpha1)이 갱신됐다. 버전 이름은 그대로고 스키마만 바뀌었다.
`c10-m1` 덤프와 `develop` 을 대조해 **Workspace 쪽 3건**을 반영하고, 어긋나 있던
`kubernetes/examples/crd.yaml` 의 참조 사본을 클러스터 기준으로 다시 맞췄다.

Operation 은 어제 `623862f`(AIP-2269)에서 `expose.inference` 가 들어가 이미 클러스터와 맞는다.
같은 expose 구조를 공유하는 Workspace 만 빠져 있었다.

설계 판단 세 가지를 남긴다.

**1. ServiceExposure DTO 를 만들지 않았다.** 이 CRD 에도 `rules[].inference` 와 `INFERENCE` enum 이
추가됐지만, 이 컨트롤러는 ServiceExposure 를 **읽지도 쓰지도 않는다** — 인포머 등록 0건, RBAC 룰
문자열 0건, 웹훅 대상 0건이다. 상위 컨트롤러(workload-controller-manager)가 Workspace/Operation 의
expose 로부터 파생 생성하는 내부 CR 이라, DTO 를 만들면 참조처 0건의 dead code 가 된다. AIP-3419 에서
Cueue DTO 를 걷어낸 것과 같은 판단이다. 스키마는 부하 프로버 사본에 반영한다(아래 "함께 보는 PR").

**2. `tools[].type` 은 `String` 으로 둔다.** CRD enum 에 `vscode` 가 추가됐지만 DTO 를 enum 으로
바꾸면 다음 tool 이 들어올 때 역직렬화가 깨진다. 컨트롤러가 이 값으로 분기하지도 않는다. 대신
`vscode` 가 그대로 실리는지를 테스트로 고정했다.

**3. 예시 CRD 는 손으로 고치지 않고 클러스터 덤프에서 기계 생성했다.** `spec.template`
(PodTemplateSpec 전문 8천 줄)만 기존 예시의 축약본으로 바꿔 끼웠다. 그 과정에서 두 가지가 드러났다 —
`operations` 예시가 **구 계약 `ports[].external`** 을 들고 있었고(DTO 는 이미 `expose`),
`workspaces` 예시는 아예 **`v1` 스키마**였다(`ssh.publicKey`·`status.addresses/pods/readyCondition`).
클러스터에 `v1` 은 없으므로 그대로 두면 적용 시 현행과 충돌한다. `v1beta1` 로 교체했다.

## Changes

**DTO — Workspace (v1beta1)**
- `V1beta1WorkspacePortExpose` 에 nested `Inference{host, path}` + 필드.
  `tls` 가 없는 것은 의도 — 추론 노출은 항상 HTTPS 라 CRD 에도 없다
- `V1beta1WorkspaceSuspendOption` 신규 (`commit{enabled, repository, applyImage}`) →
  `V1beta1WorkspaceSpec.suspendOption`
- `V1beta1WorkspaceSuspendCommitStatus` 신규 (`image, prevImage, appliedImage`) →
  `V1beta1WorkspaceStatus.suspendCommit`

**예시 매니페스트**
- `kubernetes/examples/crd.yaml` 의 `operations`·`workspaces` 문서를 클러스터 기준 재생성
  (`external` → `expose{...,inference}`, `status.ports[].type`, Workspace `v1` → `v1beta1`,
  `suspendOption`/`suspendCommit`, `vscode` 예약 포트 17682, securityContext CEL 검증)

**테스트**
- `WorkloadDtoDeserializationTest` 4건 — 인포머와 같은 Gson(`io.kubernetes.client.openapi.JSON`)
  으로 CR JSON 을 읽어 매핑을 고정

## 왜 테스트가 필요한가

리컨실 경로가 워크로드 CR 에서 쓰는 것은 `metadata.name`/소유자 라벨뿐이다. 그래서 DTO 필드명을
틀려도 **런타임에 아무 증상이 없고**, 나중에 그 필드를 읽는 코드가 생겼을 때 조용히 null 이 된다.
Gson 이 모르는 필드를 무시하는 성질이 여기선 독이라, 역직렬화를 직접 고정했다.

## 하위 호환성 · 배포 영향

- **동작 변경 없음.** 추가한 필드를 읽는 코드가 0건이고 리컨실 분기도 그대로다.
- RBAC·웹훅 `rules` 변경 없음 — 리소스 plural 과 라벨 낙인 대상 목록이 그대로다.
- 이전 빌드도 INFERENCE Workspace 때문에 죽지는 않았다(Gson 이 모르는 필드를 무시). 다만 그 필드를
  **조용히 누락**했을 뿐이고, 이번 변경으로 모델이 계약과 같아진다.
