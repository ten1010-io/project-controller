이 대화에서 팀이 공유할 만한 도메인·경계(cross-boundary) 지식·맥락을 찾아 `context/` 에 저장해주세요.

`/save-memory` 의 **팀 버전**입니다. 세 저장소의 차이:

- `/save-memory` → 개인 파일 메모리(`~/.claude/.../memory`, iCloud), 나만 봄, 내 선호·학습
- **`context/`** → git 추적(가시), 팀 전체가 clone·리뷰하는 **팀 공용 도메인 지식(SoT)** — 아직 없으면 새로 만든다
- `docs/` → 구현 **결과물(deliverables)**. 기능/작업 단위 산출(backend-dev 하네스 Phase 6 이 `docs/{작업명}/` 에 계획·구현·QA·PR 문서를 남김)

> `context/` 디렉토리가 아직 없으면 생성한다 (`context/` + `context/README.md` 인덱스).

## context/ 의 경계 (정의)

**제품 도메인 · 경계(cross-boundary) 지식** — "제품/시스템이 실제로 어떻게 동작·약속하는가".
판별 기준: **backend 코드만 읽어선 알 수 없는 것** (출처가 도메인·타 시스템·고객·정책).

- ✅ context/ : 교차 경계 계약(컨트롤러↔aipub-backend, 컨트롤러↔aipub-web 권한 표시, CRD 계약), 고객사(LGD) 특수 동작,
  외부 시스템 계약(Harbor/K8s/Elasticsearch/OIDC·LDAP 의미론), 비즈니스 규칙, 정책·로드맵,
  **제품 특성이 강제하는 패턴** (k8s-native → 리소스쿼터·admission·프록시 동작)
- ➡️ docs/ : **특정 기능/작업의 구현 결과물** (설계 결정 기록, API 명세, QA 리포트, 마이그레이션 절차)

> 경계 요령: **여러 팀·시스템이 오래 공유하는 도메인/계약 지식 → `context/`** /
> **한 기능·작업의 구현 산출물 → `docs/`** / **한 사람의 선호·학습 → `/save-memory`**

## 저장 기준 (팀에 유용 + 코드로 안 드러남)

- ✅ **함정·교차 계약** — 단일 모듈만 봐선 검증 불가한 시스템 간 계약, "이 증상이면 사실 저쪽 문제" 표지판
- ✅ **결정의 이유(ADR)** — 왜 A 대신 B 를 골랐나, 배경/트레이드오프
- ✅ **도메인 배경지식** — 비즈니스 맥락, 용어, 제약
- ✅ 반복되는 팀 합의 / 온보딩에 필요한 **도메인** 맥락

## 저장하지 않는 것

- ❌ **개인 선호·피드백** → `/save-memory` 로 (팀 SoT 오염 방지)
- ❌ 코드 / `git log` 로 알 수 있는 것
- ❌ **한 기능·작업의 구현 산출물** (설계/구현/QA/마이그레이션 문서) → `docs/{작업명}/` 로
- ❌ CLAUDE.md · docs/ 에 이미 있는 것 (중복 금지 — 링크만)
- ❌ 이번 대화에만 유효한 작업 상태 (in-progress, todo)

## 절차

1. 대화에서 위 기준에 맞는 후보를 추린다.
2. 사용자에게 후보를 보여주고 저장할 것을 선택받는다 (인자 명확하면 인자 우선).
3. `context/` 에 기록:
   - 주제 하나당 파일 하나 (`context/<kebab-topic>.md`), 상단 H1 + 본문
   - **핵심(공식·규칙·계약·매핑)은 md 본문에 직접 적는다** — Confluence/Jira/코드는 보조 링크. (AI 로 작업 시 md 하나로 파악돼야 함; 대량 참조 데이터만 외부 링크)
   - **기존에 같은 주제 파일이 있으면 새로 만들지 말고 갱신** (중복·모순 방지)
   - `context/README.md` 인덱스에 카테고리별 한 줄 포인터 추가
   - 관련 코드가 있으면 그 코드에서 이 페이지를 가리키도록 링크 제안 (SoT 1회 + 참조)
4. **커밋하지 않는다** — 워킹트리에만 반영. 커밋·PR 은 사람이 검수 후 (팀 신뢰 계층).

## 인자

- 인자 있음 → 해당 내용 우선 저장
- 인자 없음 → 대화에서 후보 추출 후 사용자 확인
